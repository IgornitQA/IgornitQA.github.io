Задача

В проекте уже существовали 13 API-сценариев авторизации. Нужно было расширить регресс и актуализировать ожидания: проверить больше вариантов входа, получение регистрационного контекста, валидацию параметров и удаление профиля.

Работал с существующим набором: сохранил предыдущие сценарии, уточнил проверки и добавил новые. Мой вклад в расширение — 20 сценариев.

Дополнительно актуализировал проверки существующих сценариев: сессии, обновление токена и профиль. Разделил API-клиенты, модели данных и проверки ответов, подготовил фикстуры для тестовых пользователей.

Поддержка и диагностика

  • Использовал модели Pydantic и отдельные проверки контрактов ответов.
  • Добавил маскирование токенов, паролей и числовых OTP во вложениях Allure.
  • Связал API-проверки с тестовой документацией, обозначив границы автоматизированного покрытия.

Как проверял результат

Для сценария удаления профиля проверки строились в три этапа:

01 / ПОДГОТОВКАОдноразовый пользователь

Фикстура создаёт пользователя и проверяет, что его профиль доступен.

02 / ДЕЙСТВИЕЗапрос к API

Тест получает OTP и выполняет запрос на удаление профиля.

03 / ПРОВЕРКАОтвет и состояние БД

Проверяет ответ API и ожидаемое изменение телефона в базе.

Такая проверка подтверждает конкретное постусловие операции: телефон в БД изменился ожидаемым образом. Одного успешного ответа API для этого было бы недостаточно.

Подготовку и очистку данных вынес в фикстуры. Предусмотрел уборку одноразового пользователя, если сценарий не дошёл до удаления.

Что получилось

Набор вырос с 13 до 33 сценариев. Регресс охватил дополнительные варианты авторизации, регистрационный контекст и удаление профиля. Проверки стали учитывать контракты ответов и состояние данных, а подготовка пользователей — повторяемой.

Для меня это пример инициативы внутри существующего проекта: найти пробелы в покрытии, добавить нужные сценарии и подготовить их к дальнейшей поддержке.

Область покрытия. Здесь описаны API-проверки авторизации и регистрационного контекста. OTP тесты получают из тестовой инфраструктуры; проверка доставки сообщений и полный UI-путь регистрации выходят за рамки кейса.

Кейс описывает личный вклад. Примеры обобщены без публикации закрытого кода, внутренних адресов и данных пользователей.
